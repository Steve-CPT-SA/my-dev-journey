CSS Loader Comparison
    Two JavaScript‑free loaders built with different techniques: a conic‑gradient ring and an SVG stroke ring. The “comparison” is between how each approach handles progress, color, and accessibility.

Known limitations
    The SVG loader’s aria-valuenow attribute is a static placeholder. The visual ring animates the value, but screen readers will always announce the fixed number. The conic loader’s DOM text is also a static “0%,” since the visible percentage is generated by a CSS counter. Neither loader exposes the animated number to assistive tech. This is deliberate: the project avoids JavaScript on purpose, so live ARIA updates are out of scope.

How it works
    A single registered --progress-value drives both loaders. It needs @property so the browser can interpolate the number smoothly.

    round() makes the counter work, because counter-reset rejects fractional values.

    Duplicate keyframe stops (e.g. 10% and 10.01%) create instant snaps, holding the color steady through each sweep. The loop seam itself (100% → 0%) has no snap stop and just relies on the animation restarting.

Conic vs SVG
    Conic ring: reveals fixed color bands as progress grows, using gradient slices.

    SVG ring: uses one stroke color per lap, snapping at boundaries, driven by dashoffset math.

    Both share the same sweepLoop and the same reset seam. The difference is in how each expresses color and progress.

Accessibility
    Reduced motion: animation is disabled and the rings freeze at 100%.

    Roles: the conic loader uses role="status", which is meant to announce changes politely. The SVG loader uses role="progressbar", which describes a value in a range. In practice, the conic percentage is CSS‑generated text, and the DOM text is static “0%.” Screen readers may not announce CSS counter changes inside a live region — test results would be needed to confirm.

Fallback
    When the @supports not (counter-reset: progress round(1)) branch is forced, both loaders show a static “0%”. This is visible but not animated. It’s a deliberate design choice to provide a placeholder when counters aren’t supported.
    Note: this fallback only covers round(). A browser without @property (for example Firefox 118–127) gets no fallback at all.

Browser support
    CSS @property: Supported in Chrome 85+, Edge 85+, Firefox 128+, Safari 16.4+, Opera 71+, and modern Android/iOS browsers.

    In browsers without @property, the sweep animation runs but the custom property isn’t registered. I expect values like --progress-value to animate discretely, flipping partway through each segment rather than interpolating smoothly.

    CSS round(): Supported in Chrome 125+, Edge 125+, Firefox 118+, Opera 111+, and Safari 15.4 (17.2 for the full set of stepped‑value functions).

    In browsers without round(), the counter-reset declaration is invalid and dropped, so Computed shows none and the percentage counter stays stuck at zero. The fallback branch shows static “0%” text.

Structure and file order
    variables.css: color tokens and sizing.

    layout.css: page layout.

    loader-base.css: shared layout, @property, keyframes, and counter logic.

    loader-conic.css: conic gradient visuals.

    loader-svg.css: SVG stroke visuals.

    loader-accessibility.css: reduced‑motion overrides, loaded last so it wins the cascade.

What I learned
    Inline style="--progress-value: …" would have overridden stylesheet rules, including reduced‑motion overrides. Presentation attributes like r="70" are different — they lose to CSS.

    inherits: false blocked values from reaching child elements — switching to inherits: true fixed it.

    Inspecting Computed in DevTools showed counter-reset: none, which led directly to the round() fix. Debugging with evidence was crucial.

    A typo in a filename taught me to check the console first when a stylesheet doesn’t apply — the error message pointed straight to the missing file.
